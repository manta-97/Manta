# Pro Layer 방향 기획 (Phase 7)

> 이 문서는 구현 명세가 아니라 **방향 고정** 문서다. Phase 7은 무료 제품이
> 한 대의 로컬 머신에서 완결된 느낌을 준 뒤에야 시작한다 — 지금은 그 경계와
> 원칙, 그리고 가장 어려운 문제(Sync)의 접근 방향만 묶어둔다.

## 1. 왜 지금 구현하지 않는가

이런 상황을 생각해보자. 로컬 제품이 아직 다듬어지는 중에 sync부터 구현하면,
이후의 모든 파일 계약 변경(frontmatter 필드, 폴더 구조, anchor 스키마)이
"동기화 호환성"이라는 족쇄를 차게 된다. 계약이 안정되기 전의 sync는
단순함을 깨는 가장 확실한 방법이다.

반대로 계약은 이미 상당히 안정됐다 — Phase 1~6을 지나며 파일 포맷, 상태 모델,
번들 포맷(`manta-tasks` v1)이 고정됐고 전부 테스트로 박제됐다. Pro Layer는
이 계약들 **위에서** 동작해야 하고, 계약을 바꿔서는 안 된다.

## 2. 무료 / Pro 경계 (확정)

| 무료 (로컬 완결) | Pro (연속성·지능) |
|---|---|
| CLI 전체 (Go, `cmd/manta`) | encrypted continuity sync (여러 기기) |
| 파일 계약 + root SQLite (`internal/engine`) | 사용자 소유 백업 대상 (S3/iCloud 등) |
| `manta context` (extractive) | semantic search (임베딩 기반) |
| Local Workspace GUI (Wails, 에디터·palette 포함) | advanced context compiler (요약·압축) |
| `manta export/import` (JSON 번들) | Jira/Notion/GitHub 커넥터 |
| Git-friendly backup | team/shared workspace (후순위) |

원칙: **무료 제품에서 데이터를 인질로 잡는 기능을 만들지 않는다.**
export가 무료인 이유가 그것이다 — 떠나는 길이 항상 열려 있어야
남아 있는 선택이 신뢰를 가진다.

## 3. Sync 접근 방향

### 3.1 출발점: 파일이 원본, 클라우드는 연속성 계층

sync 대상은 DB가 아니라 **파일**(task Markdown + anchor)이다.
root SQLite는 sync하지 않는다 — 각 기기가 자기 인덱스를 rebuild하면 된다.
이미 "DB는 삭제해도 재생성 가능"이라는 불변식이 있으므로 공짜로 얻는 성질이다.

### 3.2 단위: snapshot이 아니라 task 파일

충돌 해소가 이해 가능하려면 충돌 단위가 사람이 읽을 수 있어야 한다.
task 파일 하나가 그 단위다. 같은 task를 두 기기에서 고쳤다면:

- 상태 충돌 (폴더가 다름): 더 진행된 상태 승리 (todo < in-progress < done),
  동률이면 최근 수정 승리. 규칙이 한 줄로 설명된다.
- 본문 충돌: 자동 병합하지 않는다. 양쪽을 보존하고 (`task-3.md` + 충돌 사본)
  사람에게 보여준다. Git의 충돌 마커보다 단순하게 — 파일 두 개.

CRDT는 선택하지 않는다. 텍스트 CRDT는 "이해 가능한 충돌 해소"라는 원칙과
충돌하고(자동 병합 결과를 사람이 예측 못 함), 구현 복잡도가 단순함 원칙을 깬다.

### 3.3 암호화: 서버는 내용을 모른다

- 클라이언트 측 암호화(E2E) 기본. 서버(또는 사용자 소유 스토리지)는
  암호문 blob만 본다.
- 키는 사용자 기기에서 파생 (passphrase 기반). 키 분실 = 데이터 접근 불가를
  명시적으로 안내 — 로컬 파일이 원본이므로 실제 데이터 손실은 없다.
- 가능하면 백엔드를 추상화해서 사용자 소유 대상(S3 호환, WebDAV)을
  지원한다 — "클라우드 종속 없음" 철학의 Pro 버전.

### 3.4 식별: anchor의 projectId가 sync의 키

이미 모든 프로젝트에 영구 `projectId`가 있다 (Phase 1에서 깔아둔 기반).
기기 간 같은 프로젝트 식별은 이 ID로 한다. 폴더 경로는 기기마다 달라도 된다 —
로컬에서 이미 검증된 재연결 모델의 확장이다.

## 4. Semantic Search / Context Compiler 방향

- 임베딩 인덱스는 root SQLite 옆에 로컬로 둔다 (`~/.manta/`). 모델 호출이
  필요한 부분만 Pro API를 쓰고, 인덱스 자체는 사용자 머신에 남는다.
- `manta context`의 extractive 원칙은 무료에서 영원히 유지된다. Pro의
  context compiler는 그 위의 **추가 모드**(요약/압축)이지 대체가 아니다 —
  결정적 출력이 필요한 자동화는 계속 무료 경로를 쓸 수 있어야 한다.

## 5. 시작 조건 (이 문서를 다시 펼 때)

다음이 모두 참이 되면 Phase 7 설계를 시작한다:

1. 본인이 Manta를 일상 작업 관리에 2주 이상 연속 사용 (dogfooding)
2. 파일 계약 변경 없이 한 달 경과 (계약 안정성 증거)
3. "두 번째 기기에서 보고 싶다"는 구체적 불편이 실제로 발생

그 전까지 Pro Layer는 이 문서 상태로 동결한다.

## 6. 다섯 질문 점검

- 파일 기반 철학을 깨는가? → 아니다. sync 단위가 파일이고 파일이 원본이다.
- 단순함을 해치는가? → CRDT를 거부하고 충돌 규칙을 한 줄로 유지하는 한 아니다.
- AI 사용성을 떨어뜨리는가? → extractive context가 무료로 남는 한 아니다.
- 규약의 일관성을 약하게 만드는가? → sync가 계약 위에서 동작하는 한 아니다.
- 복구 가능성과 소유권을 해치는가? → E2E 암호화 + 로컬 원본 + 무료 export가 지킨다.
