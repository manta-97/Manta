## 초안 v1 (AI 작성, ~습니다체 — 내 말로 다시 쓸 것)

1년 전, 오래 보던 유튜버가 Claude Code 책을 냈다는 소식을 듣고 그날 바로 책을 사고 결제했습니다. 그때부터 회사 일에 에이전트를 붙여서 쓰고 있습니다.

처음 부딪힌 건 세션이 길어질 때였습니다. 초반에 "이건 하지 마"라고 정해둔 규칙이 대화가 길어지면 슬금슬금 무너집니다. compact를 해도 마찬가지였습니다. LLM은 앞말에 자연스럽게 이어지는 말을 고르는 것이라 컨텍스트가 쌓이면 당연히 생기는 일이라고 봤고, 그때부터 AI의 기억을 믿지 않게 됐습니다.

대신 문서를 믿기로 했습니다. 작업을 받으면 먼저 분석하고, 그 결과를 md 파일로 남깁니다. 계획도, 결정도 파일로 쓰게 시킵니다. 세션이 날아가도, AI가 헤매도, 내 눈에 보이는 파일이 기준이 됩니다.

회사는 Jira를 씁니다. MCP로 연결해서 에이전트가 이슈를 읽게 해봤지만 저한테는 안 맞았습니다. 매번 네트워크를 타니 미세하게 느리고, 토큰이 만료되면 에이전트가 "왜 안 되는지" 파악하는 데부터 토큰과 시간을 태웁니다. 이슈 수십 개를 훑어야 할 때는 로컬 grep이 훨씬 빠릅니다. 그리고 vim으로 읽을 수 없습니다. 사소해 보이지만 저는 글을 vim으로 읽는 사람입니다.

결정적인 건 히스토리였습니다. 저희 팀은 커밋 메시지 앞에 티켓 번호를 붙입니다. TASK-13 작업의 모든 커밋은 TASK-13으로 시작하고, 나중에 "이거 왜 이렇게 됐지?"를 추적할 때 그 접두어를 따라갑니다. 그런데 이건 "왜"는 Jira 서버에, "무엇"은 git에 갈라져 있어서 억지로 이어붙이는 방법입니다. 에이전트와 일하면 기획 문서도 코드만큼 자주 바뀝니다. 이슈 자체가 레포 안의 파일이면 "왜"와 "무엇"이 같은 git 히스토리에 남고, 접두어는 필요 없어집니다.

그래서 어느 순간부터 이슈를 md 파일로 레포 안에 두고, 에이전트가 읽고 상태를 옮기고, 저는 그 파일을 리뷰하는 방식으로 일하고 있었습니다. 주변에 이렇게 일하는 사람은 저밖에 없습니다. 다른 사람들은 AI를 꽤 믿고 빠르게 갑니다. 저는 못 믿어서 느립니다. 대신 정확하고, 무엇을 왜 했는지가 전부 남아 있습니다.

## 초안 v2 (내 첫 단락 + 번호별 주장 문장 + "결국 시간" 마무리)

저는 개발을 하면서 업무의 구체적인 작업(태스크) 문서를 코드와 같은 폴더 안에 텍스트 문서(MD 파일)로 관리합니다. 무엇을 해야 하는지, 지금 코드가 어떻고 어떻게 수정할 것인지, 왜 이렇게 결정했는지를 문서로 정리해 파일로 다룹니다. 해당 파일을 '할 일', '진행 중', '완료' 폴더에 나눠서 상태를 관리합니다. AI 코딩 도구(에이전트, Claude Code)가 그 파일을 읽고 작업해 완료 폴더로 옮기고, 저는 해당 파일을 리뷰합니다. 작업이 끝나면 해당 문서를 회사 업무 관리 도구(Jira)로 옮깁니다. 팀 규칙이고, 다른 팀원들이 Jira로 작업하기 때문입니다. 에이전트 연결 도구(MCP)도 사용하고 있지만, 아래 세 가지 이유로 MD 파일로 관리하고 있습니다.

1. 대화가 길어지면 AI에 빈틈이 생깁니다. 초반에 "이건 하지 마"라고 정해둔 규칙이 대화가 길어지면 슬금슬금 무너집니다. 대화를 요약해서 줄여도(compact) 마찬가지였습니다. 요약에 무엇을 남길지는 AI가 정하고, 빠진 게 있어도 제가 고칠 수 없기 때문입니다. 그걸 잡아내고 되돌리는 데 시간이 듭니다. 그래서 AI의 기억이 아니라 문서를 기준으로 삼기로 했습니다. 태스크를 받으면 먼저 분석을 시키고, 그 결과를 현재 상태와 목표 상태(AS-IS / TO-BE)로 나눈 문서로 남깁니다. 그 문서를 보고 계획을 세우고, 계획도 파일로 씁니다. 구현은 그 파일을 기준으로 진행합니다. 대화가 날아가도, AI가 헤매도, 제 눈에 보이는 파일이 기준이 됩니다.

2. 에이전트가 Jira를 직접 다루면 시간적 비용이 듭니다. 처음엔 MCP로 연결해서 에이전트가 Jira를 직접 읽고 쓰게 해봤습니다. 매번 서버를 거치니 미세하게 느리고, 로그인이 풀리면 에이전트가 "왜 안 되는지" 파악하는 데부터 시간을 태웁니다. 태스크 수십 개를 훑어야 할 때는 내 컴퓨터에서 바로 검색하는 게 훨씬 빠릅니다. 그리고 제가 늘 쓰는 편집기(vim)로 읽을 수 없습니다. 그래서 작업 중에는 Jira를 열지 않고 파일만 보게 됐고, Jira는 끝난 뒤 팀에 공유하는 게시판이 됐습니다.

3. 히스토리 파악이 더 빠릅니다. 저희 팀은 Jira를 단순한 할 일 목록이 아니라 기록으로 씁니다. 코드 변경 기록(커밋)마다 앞에 Jira 티켓 번호를 붙여서, TASK-13 작업의 모든 변경은 TASK-13으로 시작합니다. 버그 원인을 추적할 때도, "이건 왜 이렇게 결정했지?"를 확인할 때도 그 번호를 따라갑니다. 그런데 이 방식은 "왜"는 Jira 서버에, "무엇"은 코드 저장소(git)에 갈라져 있어서 번호로 이어붙이는 것입니다. 에이전트와 일하면 기획 문서도 코드만큼 자주, 많이 바뀝니다. 태스크가 코드 옆의 파일이면 "왜"와 "무엇"이 같은 기록에 남고, 찾아가는 단계가 하나 줄어듭니다.

하나하나는 몇 분짜리 낭비입니다. 하지만 이게 하루에도 여러 번 반복되고, 에이전트가 헤매는 시간은 그대로 토큰 비용이기도 합니다. 그리고 시간보다 더 큰 이유가 있습니다. AI가 무엇을 기억하고 있는지를 저는 제 눈으로 보고, 제 손으로 고치고 싶습니다. 파일이면 제가 읽고, 고치고, 다음 작업에 이어서 쓸 수 있습니다. AI를 완전히 믿지 않아서 속도는 좀 느리지만, 결과가 정확하고 무엇을 왜 했는지가 전부 남아 있습니다.

Manta는 이 작업 방식을 그대로 도구로 만든 것입니다. 사용자 1호가 저라서, 무엇이 필요하고 무엇이 필요 없는지 이미 알고 있습니다.

## 인터뷰 재료 (2026-09-16)

### 지금 어떻게 일하나
- **정확한 흐름**: 레포 안 md로 작업 관리 → 작업 완료 시 그 문서를 **Jira로 옮긴다** (Jira를 버린 게 아니라, 작업은 파일에서 하고 마지막에 동기화)
  - 옮기는 방법: **직접 복붙**. MCP로 시키는 것보다 빠르고 덜 귀찮음
  - 왜 Jira를 안 버리나: **팀 규칙**. 다른 팀원이 Jira를 봄
  - → Manifesto 7장 Sync, 데모의 Jira import와 직결되는 지점

### 나아갈 방향 (Q3-2 수익, Q4-1 사업화 재료)
- 개인: PC 기반, 로컬 (무료)
- 동기화(sync): **유료**. 팀 규모가 커지면 sync되도록
- 작업을 받으면 먼저 분석 → 분석 결과는 **별도 문서**로 남긴다
- Claude Code / Codex를 TUI에서 쓰는 걸 선호
- TUI 세션의 문제
  - 실수로 세션을 나가면 다시 찾는 게 일
  - **가장 큰 이유**: 세션이 길어지면 compact를 해도 핵심에서 벗어남 → 그걸 내 눈으로 문서로 보며 관리하고 싶었다
  - 그래서 AI에게 **문서로 직접 작성하게 시키는 것**을 선호

### 회사 Jira + MCP 경험 — 왜 불편한가
- 회사는 Jira. MCP로 연결해 쓴다
- 불필요한 네트워크 통신 → 사소한 딜레이. 토큰 만료되면 재로그인까지, 더 오래 걸림
- 개인적 이유: **vim으로 읽을 수 없다**. 글은 vim으로 읽는 게 편하다
- task를 대량으로 찾을 때 Jira MCP는 느리다. 로컬 검색이 훨씬 빠르다
- **가장 중요**: 히스토리 추적. AI가 코드도 많이 만들지만, 기획 문서도 빨리·많이 수정된다 → 그 변경 히스토리 트래킹이 매우 중요 → 그래서 md 파일을 로컬에서 직접 쓴다

### 세션이 길어지면 무슨 일이 생기나
- 초반에 지정한 규칙을 안 지킴. "이 행동은 하지 마"라고 했는데 대화가 길어지면 무너짐
- 내 해석: LLM은 결국 자연스러운 말 잇기 → context가 쌓이면 당연히 생기는 현상
- (특정 사건은 기억 안 남 — 반복적으로 겪은 패턴)

### Jira MCP 재로그인
- 자주는 아님. 그런데 한 번 발생하면 AI가 **그 상황을 파악하는 것부터** 토큰 낭비·시간 낭비

### 히스토리 — 매우 많이 뒤져본다
- Jira를 단순 todo가 아니라 **히스토리 저장소**로 쓴다. 나중에 특정 작업의 맥락 파악에 매우 중요
- 그래서 커밋 메시지 접두어가 Jira 티켓 번호: `TASK-13` 작업의 모든 커밋은 `TASK-13 ...`
- 요기요에서 이렇게 했다고 들은 것 같음 → 조사 필요

### 조사: 티켓 번호 접두어 관행
- 요기요 사례는 공개 자료 없음 (내부 컨벤션이라 확인 불가 → 지원서에 회사명 언급 X)
- 일반 명칭: Atlassian **Smart Commits** — 커밋 메시지에 `PROJ-123` 키를 넣어 Jira 이슈와 커밋을 연결. 널리 쓰이는 관행이고 commitlint 플러그인, git hook으로 강제하는 팀도 많음
- 지원서 관점의 함의: 이 관행은 **"작업의 히스토리는 결국 git에 있다"** 는 걸 모두가 인정하는 증거. 그런데 티켓(왜) 은 Jira 서버에, 코드(무엇) 는 git에 갈라져 있어서 접두어로 억지로 이어붙이는 것. 이슈가 레포 안의 파일이면 이 연결이 자연스럽게 하나의 git 히스토리로 합쳐진다
- 출처: [Atlassian Smart Commits](https://support.atlassian.com/jira-software-cloud/docs/process-issues-with-smart-commits/) · [자동 접두어 hook 글](https://medium.com/bytelimes/automate-issue-numbers-in-git-commit-messages-2790ae6fe071)
