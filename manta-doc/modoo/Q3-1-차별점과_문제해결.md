## 초안 v1 (AI 작성, ~습니다체 — 내 말로 다시 쓸 것)

**해결하려는 문제**

개발자는 이제 터미널에서 AI 코딩 도구(에이전트)와 함께 일합니다. 그런데 그 일을 관리하는 도구는 여전히 웹 브라우저 안, 서버 위에 있습니다. 일이 일어나는 곳과 일을 기록하는 곳이 다르니, 개발자는 매번 그 사이를 오가며 시간을 씁니다. Manta는 개발 업무(태스크)를 텍스트 문서(MD 파일)로 코드 옆에 두고, 사람과 AI가 같은 파일을 다루게 해서 이 간격을 없앱니다.

**기존 도구에서 배운 것**

저는 기존 도구를 나쁘다고 보지 않습니다. 각각이 무엇을 잘했고 어디서 멈췄는지를 보고, 가져올 것과 바꿀 것을 정했습니다.

Jira는 기능이 가장 많지만 느립니다. 웹 기반이라는 한계 위에 기능이 쌓여 더 무거워졌습니다. 그 빈틈에 Linear가 들어왔습니다. Linear의 속도와 단축키 중심 사용성은 제가 가장 높게 평가하는 부분입니다. 조사해 보니 그 속도의 비밀은 화면이 아니라 구조였습니다. Linear는 데이터를 사용자 브라우저에 먼저 저장하고 서버와는 뒤에서 맞추는 로컬 우선(local-first) 구조를 만들었습니다. 시장도 그 방향으로 움직이고 있습니다. 2026년 2~4월 신규 도입 기업은 Linear 1,351곳, Jira 1,524곳으로 거의 따라붙었고, Linear 고객은 AI 코딩 도구 채택률이 눈에 띄게 높습니다.

Obsidian에서는 철학을 가져옵니다. 데이터는 로컬에 있고 사용자가 소유해야 한다는 것입니다. AI 에이전트가 파일을 직접 읽고 쓰는 시대에 이 원칙은 더 중요해졌습니다. 다만 Obsidian은 문서 도구입니다. 태스크에는 상태가 있고 코드 저장소(레포)마다 따로 관리되어야 하는데, 저장소가 여러 개면 동기화 비용이 그만큼 커집니다. Notion과는 용도가 다르다고 봅니다. 문서는 여러 사람이 동시에 고쳐야 하지만, 태스크는 대부분 한 사람의 것입니다. 그래서 공유의 속도보다 개인의 속도가 먼저입니다.

**Manta가 다른 점**

1. 파일이 원본이고, 코드 옆에 있습니다. Linear는 로컬에 사본을 두어 빨라졌습니다. Manta는 그 길을 끝까지 갑니다. 태스크가 코드 저장소 안의 파일로 존재하고, 서버가 없어도 완결됩니다. 그래서 속도는 로컬 프로그램의 속도이고, 저장소마다 태스크가 자연스럽게 나뉘며, Git으로 코드와 함께 추적됩니다.

2. AI가 직접 사용하는 도구입니다. Manta는 명령줄 도구(CLI)와 에이전트용 작업 지침(skill)을 함께 제공합니다. 태스크를 만들고, 수정하고, 구체화하는 일은 에이전트가 하고, 사람은 결과를 검토합니다. 파일이 기준이기 때문에 Claude Code든 Codex든 어느 에이전트로 바꿔도 같은 태스크를 이어서 다룹니다.

3. 개발자와 기획자를 나눕니다. 이것이 "그냥 MD 파일과 Git으로 하면 되지 않나"라는 질문에 대한 답입니다. 개발자 혼자 태스크를 관리하지 않습니다. 실제로는 Git이 익숙하지 않은 기획자와 PO가 더 많이 다룹니다. 그래서 개발자는 로컬 파일과 CLI에서, 기획자는 웹에서 같은 태스크를 봅니다. 동기화(sync)는 백그라운드에서 돌고, 끝나기를 기다렸다가 다음 일을 하지 않습니다. 이 역시 Linear가 증명한 방식입니다. 소통은 여전히 사람이 하고, 시스템은 변경을 알려주는 데까지만 합니다.

**지금 어디까지 왔나**

이 방식은 제가 1년 넘게 실제로 일해 온 방식입니다. 도구만 없었을 뿐입니다. 구조는 단순합니다. 원본은 파일, 검색용 인덱스는 언제든 다시 만들 수 있는 로컬 DB, 서버는 동기화 단계에서만 필요합니다. 지금은 첫 데모(Manta Pup)로 태스크 생성·수정·목록·필터와 기존 Jira 이슈 가져오기를 만들고 있습니다.

## 초안 v2 (Q2 스타일 — 오프닝 + 번호별 주장 문장 + 구체 장면 + 마무리)

저는 같은 문제를 푸는 도구들을 꽤 많이 써봤습니다. 회사에서는 Jira를, 개인 프로젝트에서는 Linear, Notion, Obsidian을 썼고, 지금은 MD 파일과 Git으로 일합니다. 어느 것도 나쁜 도구는 아니었습니다. 각각 잘하는 것이 분명했고, 멈춘 지점도 분명했습니다. Manta는 그 장점을 가져오고, 멈춘 지점을 바꿉니다. 기존 도구와 다른 점은 세 가지입니다.

1. 속도는 로컬에서 나옵니다. 회사에서 쓰는 업무 관리 도구(Jira)는 기능은 가장 많지만 느립니다. 페이지를 열 때마다 기다리고, 화면마다 채워야 할 항목이 수십 개입니다. 그 빈틈에 Linear가 들어왔습니다. 단축키 하나로 상태를 바꾸는 속도감과 개발자 편의성은 제가 가장 높게 평가하는 부분입니다. 조사해 보니 그 속도의 비밀은 화면이 아니라 구조였습니다. Linear는 데이터를 사용자 브라우저에 먼저 저장하고 서버와는 뒤에서 맞추는 로컬 우선(local-first) 구조를 만들었습니다. 2026년 2~4월 신규 도입 기업은 Linear 1,351곳, Jira 1,524곳으로 거의 따라붙었고, Linear 고객은 AI 코딩 도구 채택률이 눈에 띄게 높습니다. Manta는 Linear가 반쯤 간 길을 끝까지 갑니다. 로컬에 사본을 두는 게 아니라, 태스크 자체가 코드 저장소 안의 텍스트 문서(MD 파일)로 존재합니다. 태스크를 여는 것은 파일을 여는 것이고, 목록은 폴더이고, 검색은 내 컴퓨터 검색입니다. 서버가 없어도 완결되니 인터넷이 끊겨도 일이 멈추지 않고, 저장소마다 태스크가 자연스럽게 나뉘고, 코드와 함께 Git으로 기록됩니다.

2. AI가 직접 사용하는 도구입니다. 로컬 파일의 철학은 Obsidian에서 가져왔습니다. 데이터는 내 컴퓨터에 있고 내가 소유한다는 원칙인데, AI 에이전트가 파일을 직접 읽고 쓰는 시대에는 이 원칙이 더 중요해졌습니다. Manta는 태스크 파일의 형식을 정하고, 그 파일을 다루는 명령줄 도구(CLI)와 에이전트용 작업 지침(skill)을 함께 제공합니다. 제가 "이 버그를 태스크로 만들어"라고 하면 에이전트가 CLI로 파일을 만들고, 코드를 분석해 현재 상태와 목표 상태(AS-IS / TO-BE)를 채우고, 진행 중으로 옮깁니다. 저는 화면에서 목록을 확인하고, 내용을 읽고, 틀린 곳을 고칩니다. 만들고 수정하고 구체화하는 일은 에이전트가 하고, 사람은 검토합니다. 기준이 파일이기 때문에 Claude Code에서 Codex로 에이전트를 바꿔도 같은 태스크를 그대로 이어서 다룹니다.

3. 개발자는 저장소 안에서, 기획자는 하나로 모아서 봅니다. "그냥 MD 파일과 Git으로 하면 되지 않나"라는 질문에 대한 답이기도 합니다. 실제로는 Git이 익숙하지 않은 기획자와 PO가 태스크를 만들고 우선순위를 정합니다. 그리고 회사 일은 레포 하나에 태스크 하나가 아닙니다. 프론트엔드 레포와 백엔드 레포에 각각 태스크가 있고, 개발자는 자기 레포 안의 파일만 보면 되지만 PO는 두 팀의 태스크를 한 화면에서 봐야 합니다. Obsidian처럼 저장소마다 따로 두면 이게 안 됩니다. 그래서 서버에 프로젝트를 만들고 레포를 여러 개 연결하면, 각 저장소의 태스크 파일이 뒤에서(sync) 서버로 모이고 기획자는 웹에서 프로젝트 단위로 봅니다. 개발자 쪽에서 이 동기화는 백그라운드에서 돌아갑니다. 저장하면 내 화면에는 바로 반영되고, 서버로 보내는 일은 뒤에서 처리되며, 끝나기를 기다렸다가 다음 일을 하지 않습니다. 이 지점에서 Notion과 용도가 갈립니다. 문서는 여러 사람이 동시에 고쳐야 하니 공유의 즉시성이 중요하지만, 태스크는 대부분 한 사람의 것입니다. 몇 초 늦게 공유되어도 괜찮고, 개인의 속도가 먼저입니다. 소통은 여전히 사람이 하고, 시스템은 변경을 알려주는 데까지만 합니다.

이 방식은 제가 1년 넘게 실제로 일해 온 방식이고, 도구만 없었을 뿐입니다. 구조는 단순합니다. 원본은 파일, 검색용 인덱스는 언제든 다시 만들 수 있는 로컬 DB, 서버는 동기화에만 필요합니다. 지금은 첫 데모(Manta Pup)로 태스크 생성·수정·목록·필터와 기존 Jira 이슈 가져오기를 만들고 있습니다. Jira 가져오기는 Jira를 대체하기 위한 입구입니다. 개발자는 로컬에서 빠르게, 기획자는 Git 없이 편하게, 이것이 Manta가 풀려는 문제입니다.

## 최종

저는 같은 문제를 푸는 서비스를 많이 사용해봤습니다. Jira, Linear, Notion, Obsidian 등을 다양하게 사용 중이고 어느 것도 나쁜 도구는 아니라고 생각합니다. 각각 좋은 점이 있었고, 불편한 점도 있었습니다. Manta는 장점은 그대로 가져오고, 불편했던 점은 제 방식대로 바꾸려고 합니다.
1. 속도는 로컬에서 나옵니다. Jira는 기능이 가장 많지만 가장 느립니다. 페이지를 열 때마다 기다리고, 화면마다 채워야 할 항목은 수십 개입니다. 그 빈틈에 Linear가 들어왔다고 생각합니다. Linear의 속도감과 개발자 편의성(단축키 등)은 제가 가장 추구하고 싶은 방향입니다. Linear는 데이터를 사용자 브라우저에 먼저 저장하고 서버와는 뒤에서 맞추는 로컬 우선(local-first) 구조를 만들었습니다. 왜냐하면 이렇게 해야 빠르기 때문입니다. Manta는 Linear가 반쯤 간 길을 끝까지 갑니다. 로컬에 사본을 두는 게 아니라 태스크 자체가 코드 옆에 텍스트 문서(MD 파일)로 존재합니다. 태스크를 여는 것은 파일을 여는 것이고, 목록은 폴더입니다. 서버를 거치지 않으니 기다리는 시간 자체가 없습니다. Linear가 브라우저 안에서 만든 속도를, Manta는 제 컴퓨터에서 그대로 냅니다.
2. AI가 직접 사용하는 도구입니다. 로컬 파일의 철학은 Obsidian에서 가져왔습니다. 데이터는 내 컴퓨터에 있고 내가 소유한다는 원칙인데, AI 에이전트가 파일을 직접 읽고 쓰는 시대에는 해당 원칙이 더 중요해졌다고 생각합니다. Manta는 태스크 파일의 형식을 정하고, 그 파일을 다루는 명령줄 도구(CLI)와 에이전트용 작업 지침(skill)을 함께 제공하려고 합니다. 사용자가 '이 버그를 태스크로 만들어'라고 하면 에이전트가 CLI로 파일을 만들고, 코드를 분석해 현재 상태와 목표 상태(AS-IS / TO-BE)를 채웁니다. 사용자는 내용을 직접 확인하고 승인하면, 에이전트가 작업을 수행하고 상태를 변경합니다. 또한 기준이 대화 세션이 아니라 파일이기 때문에 다양한 에이전트를 상황에 맞게 사용할 수 있습니다.
3. 개발자들은 각각의 코드 저장소(레포) 안에서, 기획자는 프로젝트 하나로 모아서 봅니다. '그냥 MD 파일과 Git으로 하면 되지 않나'라는 질문의 답이기도 합니다. Git이 익숙하지 않은 기획자와 PO가 태스크를 만들고 우선순위를 정합니다. 그리고 그 태스크는 레포 하나에서 작업되지 않습니다. 프론트엔드 레포, 백엔드 레포 등 다양한 레포에 각각의 태스크가 있고, 개발자는 자기 레포의 파일만 보면 되지만 PO는 모든 팀의 태스크를 확인해야 합니다. Obsidian처럼 레포마다 따로 두면 통합 관리가 안 됩니다. 그래서 서버에 프로젝트를 만들고 레포를 여러 개 연결해 각 저장소의 태스크 파일을 서버로 모아서(sync) PO가 웹에서 프로젝트 단위로 확인할 수 있도록 하려고 합니다. 개발자 입장에서 해당 동기화는 백그라운드에서 돌아갑니다. 이 지점에서 Notion과 용도가 갈립니다. 문서는 여러 사람이 동시에 고치는 경우가 많아 즉시성이 중요하지만, 태스크는 대부분 한 사람이 작업하고 결과를 공유하는 방식이라 공유가 조금 늦어도 괜찮습니다. 오히려 개인의 작업 편의성과 작업 속도가 더 중요하다고 생각합니다.
이 방식은 제가 1년 넘게 실제로 일해 온 방식이고, 도구만 MD, Git, Jira로 나눠져 있었을 뿐입니다. 이 작업을 Manta라는 하나의 도구로 관리하려는 것입니다.

### 1. 기존 도구를 어떻게 보는가
- **Jira**: 싫어하는 도구. 핵심 불만은 **느리다**. 웹 기반 + 기능 과다 + 복잡함. 그중 가장 큰 건 속도.
- **Linear**: Jira의 그 빈틈(속도)에 들어와 성장했다고 본다. 속도감과 개발자 편의성(단축키)을 높게 평가. Linear도 웹 기반이지만 사용성으로 극복 — "기술적으로 먼저 보여줘야 하는 것들을 잘 정리한 느낌".
  - Manta는 Linear의 빈틈에 들어간다: Linear는 웹, Manta는 **로컬이라 진짜 빠르다**.
- **Notion**: 태스크 관리는 노션과 다르다. 노션은 여러 명이 문서를 함께 고쳐야 하니 공유 속도가 중요. **태스크는 주로 한 사람의 것** → 동기화(sync) 속도는 늦어도 되고, **개인의 속도**가 중요.
- **Obsidian**: 정말 좋아하는 도구. 노션보다 선호하는 이유는 **로컬**. AI 에이전트 시대에 로컬의 중요성이 더 크다.

### 2. 가장 큰 적: "md 폴더 + git"
- 기존 제품보다 더 큰 적은 "그냥 md 폴더 + git"이다.
- 하지만 개발자 혼자 태스크를 관리하지 않는다. **git이 익숙하지 않은 기획자·PO가 오히려 태스크 관리를 한다** → 결국 서버가 필요.
- 그래서 나눈다: **개발자는 로컬에서 자유롭게, 기획자는 git 없이 편안하게.**

### 3. Jira와의 관계
- Jira를 **사용하지 않게** 하고 싶다. (대체. 데모의 Jira import는 옮겨오는 입구.)

### 4. AI가 사용자다 — 구체적으로
- Manta는 **skill + CLI를 함께** 낸다. 정형화된 skill과 CLI를 에이전트가 쓰게 한다.
- 태스크를 만들고, 수정하고, 구체화하는 **모든 것을 에이전트와 CLI가** 한다. 사람은 **감시(검토)** 한다.

### 5. 지금 되는 것
- 없음 (Pup 골격만). 실현가능성은 다른 근거로 채워야 함.

### 6. 해결하는 문제 한 줄
- 모두가 편안하게: **개발자는 로컬에서 빠르고 편안하게, 기획자는 git 같은 지식 없이도 편안하게.**

### 조사: Linear는 왜 빠른가 (2026-09-16)
- Linear의 속도는 단축키·UI만이 아니라 **자체 sync engine** 덕분. 브라우저 IndexedDB를 진짜 DB처럼 쓰고, 모든 변경을 **로컬에 먼저 반영(optimistic update)** 한 뒤 백그라운드로 서버와 동기화. 즉 Linear는 "웹이지만 **local-first**"로 속도를 만들었다.
  - 출처: performance.dev "How's Linear so fast", fujimon.com "Linear's sync engine architecture", Tuomas Artman 발표(Local First Conf), github wzhudev/reverse-linear-sync-engine
- 시사점: Linear가 증명한 건 "**데이터가 로컬에 있으면 빠르다**". Manta는 그걸 끝까지 간다 — 로컬 캐시가 아니라 **파일 자체가 원본**, 서버 없이도 완결.
- 성장 데이터 (Bloomberry, 2026-05): 2026년 2~4월 신규 고객 Linear 1,351 vs Jira 1,524. 전년 동기 대비 Linear +67%, Jira −32%. Linear 고객의 72.6%가 11~200인 기업. **Linear 고객은 AI 코딩 도구 채택률이 매우 높음(Cursor 73x lift)** → "AI 시대 개발팀"이 Linear로 이동 중.
- Linear 기업가치 $1.25B (2025-06, Series C $82M, Accel).
- 시장 점유 (Lenny's Newsletter 2025-01): Jira 68%, Linear 10%. 그러나 Linear가 가장 빠르게 성장하는 대안.

### 7~10 후속 답변
- **7. sync 그림**: 로컬 first. 웹 + PC 프로그램 모두에서 본다. **sync는 백그라운드 작업** — 완료돼야 다음 일을 할 수 있는 게 아니다. Linear의 방향을 따라간다.
- **8. 실현가능성**: 1년간 일해 온 방식이고 기능만 아직 없다. 이걸 만들 능력은 회사 다니면서 계속 학습해 왔다.
- **9. 기획자→에이전트 자동 구체화?**: 아니다. **소통은 결국 사람**. 시스템은 수정사항 **알림** 정도.
- **10. Obsidian**: 직접 태스크 관리에 쓸 수도 있다. 문제 2가지 — (1) 코드 저장소(레포)가 생각보다 많은데 여러 vault를 sync하려면 유료 (Sync Standard $4/월 1 vault, Plus 10 vault) (2) 결국 개인 프로젝트에만 유리. 팀 sync는 가성비도 용도도 안 맞음. **가져오는 건 철학: 로컬, 개인 소유.**

### 주제 정리 (초안 골격)
0. 문제 한 줄: 일은 터미널·로컬에서, 기록은 웹·서버에 → 간격
1. 기존 도구에서 배운 것: Jira(느림) → Linear(속도, 비밀은 local-first sync engine; 시장 숫자) / Obsidian(로컬·소유 철학; 그러나 문서 도구, 레포 多, sync 비용) / Notion(문서는 동시편집, 태스크는 한 사람)
2. Manta가 다른 점 3가지: ① 파일이 원본, 코드 옆 (Linear가 반쯤 간 길을 끝까지) ② AI가 직접 사용 (skill + CLI, 사람은 검토, 에이전트 무관) ③ 개발자 로컬 / 기획자 웹, sync는 백그라운드, 소통은 사람 → "md+git이면 되지 않나"의 답
